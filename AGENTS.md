## 1. Purpose and scope

The project does two things:
1. **Full control and monitoring of what the controller exports** (since v0.8.0, SMA-106): every function becomes the richest entity its datapoints support — `light`, `switch`, `cover`, `climate`, `lock` — and **every datapoint the composite does not consume becomes its own entity** (`sensor`, `binary_sensor`, `select`, `number`, `switch`, scene `button`). Nothing the controller publishes is invisible. Plus controller health and export diagnostics on the controller device.
2. **Controller backups**: download the password-protected *system* and *project* ZIP backups from the controller's management API, store them in `<HA config>/wiser_backups/`, schedule them, prune old ones, and take a fresh one before every Home Assistant backup.

History worth knowing: binary_sensor, cover, climate and the function-derived sensors were **removed in v0.5.0** and **re-added in v0.8.0** on the owner's instruction, now built on the measured `dic:dpa.*` role map instead of title heuristics. `__init__.py` no longer deletes any entity (`_remove_unsupported_entities` and `_SENSOR_SUFFIXES` are gone) — every exported type has a platform again, and a datapoint missing from a poll means a failed read, not a deleted device. Do not re-introduce an entity sweep.

Deliberately **not exposed**: restore, admin password change, hostname change, KNX/BACnet patches, log clearing. This is a **policy choice, not an absence of endpoints** — the earlier claim that "no path to them exists" was **measured wrong on 2026-11-22**: the `management` app owns 39 operations on `/api/management/v1`, all answering 200 with the ordinary admin credential, including `scada-main/general/restore`, `flashsys/system/RestoreConfiguration`, `PATCH flashsys/system/hostname`, `PATCH flashsys/Network/KNCConnection` (the KNX connection itself), `POST flashsys/system/AdminAccess`, `DELETE scada-main/ErrorLogs` and the `project_backups`/`ets_project_backups` families. Reboot/shutdown remain genuinely off this surface. Do not add any of these without an explicit instruction: a one-click restore or KNX-connection patch in Home Assistant is a destructive action one mis-tap away. Keep out of any future diagnostics: the BACnet settings carry a `Password` field, and `flashsys/Network/Interfaces` hands out the unit's **MAC** on a plain read (the same round also reports a **service tag** in `custom/deviceInfo`, which this repo's own live read on 2026-11-21 did not see — unreconciled, and it changes nothing: `health.parse_health` whitelists the seven fields it keeps instead of forwarding the payload, so keep that shape). Also deliberately absent: the controller's own scenes/schedulers/automations (not on the 3rd-party API), history backfill from `vis/graph` (it reads `objectlog` and object ids are recycled).

## 3. How it works

**Config flow** (`config_flow.py`): `user` (manual) or `zeroconf`/`dhcp` → `credentials` → verify (`discover_endpoints` + `authenticate`) → `backup` step (password, interval hours default 24, keep default 7, "create a backup right away" default on) → entry created with `data` (host, port, ssl, verify_ssl, username, password, api_base) and `options` (backup_*). The "backup now" flag is passed to setup through `hass.data[DATA_INITIAL_BACKUP]` (a set of unique ids). An empty password means backups are skipped until set in Configure. The options flow keeps the existing password if the field is left empty and validates new ones. `OptionsFlow.config_entry` comes from the base class (HA ≥ 2024.12); do not set it in `__init__`.

**Setup** (`__init__.py`): builds `WiserKnxClient`, coordinator, first refresh (failure → `ConfigEntryNotReady`), `WiserKnxBackupManager` (stored as `coordinator.backup_manager`), registers the controller device, registers the `wiser_for_knx.create_backup` service once, forwards platforms, and runs the initial backup in a background task (one retry after 60 s). Options changes reload the entry. It deletes **no** entities.

**Polling**: `coordinator._async_update_data` fetches datapoints every `scan_interval` seconds (default 10) and locations/functions on the slow `STATIC_*` cadence into a cache (hourly, retried every 5 min, dropped after 3 h of failures; `async_refresh_structure` is the "Rescan devices" button). At the end of a successful poll it stores `coordinator.entity_plan = plan_entities(functions)` — once per poll, not once per platform.

**Entity model** (the part to understand before touching any platform):
1. `widgets.classify_function(func)` → a category from the **function** (widget id, then substrings of the *whole* KNX URN, then datapoint titles, then the function title; default `sensor`).
2. `datapoints.datapoint_role(dp)` → a role from the **datapoint's `dic:dpa.*` archetype**, which identifies the Touch *slot* it came from. The `dpt.*` type is only a fallback and `None` is a valid answer. Never classify a datapoint by its title (user-defined group object names) or by its unit.
3. `plan.plan_entities(functions)` → `{platform: [spec]}`. A composite (light/switch/cover/climate/lock) is built only if `composite_is_viable` finds the writable roles it needs; it consumes the roles in `COMPOSITE_ROLES` and **every remaining datapoint gets its own entity** via `datapoint_platform`. A category that cannot be supported degrades to datapoint entities instead of producing a broken composite.
4. `entity.async_setup_plan_entities` adds a platform's entities at setup *and* on every later poll, keyed by `spec["key"]`, and never removes anything.

Unique ids: a composite is `{DOMAIN}_{entry_id}_{function_id}` (unchanged since v0.1, so existing light/switch entities survive the v0.8.0 upgrade) and a datapoint entity is `{DOMAIN}_{entry_id}_{datapoint_id}`; both ids are stable across widget edits, group-address changes and renames.

Adding support for something new: put the decision in `datapoints.py` (a role) and `plan.py` (a platform) with a unit test, and keep the platform file thin. A new `dic:dpa.*` row must come from a measurement — the skillset's `widget-api-matrix.json` — not from a guess.

**Writes**: `PUT {api_base}/datapoints/values` with JSON:API body; HTTP 200/201/202/204 = success (the controller answers 202 Accepted).

**Backups**: `POST /api/management/v1/flashsys/system/backupConfiguration` and `/scada-main/general/backup` with JSON `{"data":{"password": "..."}}`. Returns a password-protected ZIP. Each payload is parsed as a ZIP before anything is written; files are written to a temp name, `chmod 0600`, and renamed; pruning is per kind and per host. Errors raise `HomeAssistantError` and are stored in `last_error`. HA hooks `async_pre_backup`/`async_post_backup` in `backup.py` refresh the backups before each HA backup and never block it.

## 4. Controller facts agents must know (details in docs/controller-api.md)

- HTTPS, usually a self-signed certificate (verification is on by default since v0.7.0-beta.1 and self-signed certificates are trusted by pinning their fingerprint during setup), HTTP Basic auth, user `admin`.
- The 3rd-party API at `/api/w4knx/3rdparty/v1` serves `application/vnd.api+json` and the `Accept` header **must match it verbatim or by wildcard**. Full matrix measured 2026-11-22: `*/*`, `application/*`, `application/vnd.api+json` and any list containing `*/*` (e.g. `application/json, */*`) answer **200**; `application/json` alone, `text/*` **and an absent `Accept` header** answer **406**. So the rule is not "json is wrong", it is "match the served type or wildcard it, and never omit the header". `api.py::_get_headers` sends `application/vnd.api+json, application/json` and the two `/.well-known/knx` probes send `application/json, */*` — both land in the 200 column; dropping the `*/*` from a probe would silently turn every answer into a 406 (that trap hid a 404 for a whole round in the skillset's rig).
- The management API `/api/management/v1` uses the same host, port and credentials, and is **HTTPS-only** (it answers 406 over plain HTTP, and 403 to a method outside `GET|POST|PUT|DELETE|PATCH`). It is a 39-operation control surface, not just the two backup endpoints this integration calls (§1).
- Touch widget ids (`se-light-switch`, …) are **not** in the API; classification works from KNX function URNs (`switchingLight`, `dimming`, `switchingSocket`, `switching`, …). Vendor URNs exist (`fct.schneider.logicThermostat.type.thermostat`), so match on the whole URN — never split on `.` and take a segment.
- A datapoint's `meta["@type"]` carries **two** tags: a `dic:dpa.<archetype>` and a `urn:knx:dpt.<type>`. The archetype identifies the **Touch slot** the datapoint came from, which nothing else in the API exposes, and it is the only way to tell apart slots that share a `dpt.*`: `dpa.800.65` height vs `dpa.800.66` slats, `dpa.65533.51` battery level vs `.52` low-battery, `dpa.399.56` current temperature vs `dpa.392.5x` setpoints, and — the one that bites — `dpa.417.72` a thermostat's own on/off vs `dpa.417.70` its **fan manual mode**, both writable `dpt.switch` on the same function. The full measured table is `datapoints.py::DPA_ROLES`.
- Backup password rule: ≥ 8 characters with an upper-case letter, a lower-case letter and a digit.
- A backup response has **no JSON envelope and no `success` key — the body is the ZIP**, so HTTP 200 proves nothing. `backup_utils.zip_entry_count` parses it before `backup.py` stores it. Validate by parsing and counting entries, **never by byte size**: the project archive's size drifts upwards with the trend data inside it (452133 B measured on 2026-11-20 against the 423–431 KB recorded earlier) while the entry count stayed put. Stored files are `chmod 0600`.
- `/datapoints` and `/functions` answer **500** intermittently (export being recomputed) and *permanently* while an `se-danfoss-thermostat` widget has its `object-device-status` slot populated. 5xx is retried in `api.py`; a failed poll is "no new data", never an empty installation. Never delete entities because a refresh failed.
- Writes answer **202 before deciding**: a value that is not a member of the datapoint's `enum` verbatim is accepted and silently discarded. `coordinator._enum_member` maps to the published spelling.
- An enum member is encoded **by name, not by its position in the published list** (measured 2026-11-21, API write watched on the bus): `dpt.heatCool` is published `["heat","cool"]` and `heat` puts raw `01` on the object, `cool` raw `00` — DPT 1.100's order, the reverse of the list. Encode and decode agree, and 2026-11-22 added `dpt.step` (`increase` raw `01`, `decrease` raw `00`), `dpt.upDown` (`up` raw `00`) and `dpt.deviceStatus` (`online` raw `00`). So never infer a raw value from the order of `enum` — ask `datapoints.enum_member_for_bit`, which answers only from measured pairs and is entitled to answer `None`.
- The export is a **cache**, regenerated by the controller's `apit3` app daemon when the Touch config CRC changes, while values reach the API separately. Measured 2026-11-21 with that daemon not running: `/functions` and `/datapoints` answer 200, values stay live, and **no new widget ever appears**. Starting it (2026-11-22, the vendor's `apps.daemon` launcher, owner-authorised) made both waiting widgets export in the next poll, and the export tracked their teardown back down afterwards. Nothing on the controller supervises an app daemon, and that is now measured the hard way rather than read off a config: on 2026-11-22 the skillset killed the `apit3` daemon with a live subscription in place and **nothing restarted it within 120 s** (`procmon` runs minutely and is the one thing that would — the two rounds disagree on why, an entry list for the SCADA core/nginx/redis/OpenVPN in the earlier reading versus an empty config directory in the later one, and only the conclusion is load-bearing here). That unit also had no `apit3` pidfile since its last boot, so **a reboot is not a reliable fix**, and `apit3` is already at the store's latest build (`20260909`), so neither is an app update. 🪤 The authorised reboot of 2026-11-25 pulls the other way without settling it: `apit3` was running again 34.5 s after the trigger, under a new pid — but that box's daemon was *alive* beforehand, and nobody has rebooted one whose daemon was dead. Unreconciled, and the advice is unchanged: reboot if you like, then add a widget and check that it appears. A frozen export is indistinguishable from a complete one from inside Home Assistant - do not add a detector for it, and do not read "the API answers" as "the export is current". The mechanism behind that is now measured (2026-11-22): **`apit3` is two components and only one of them is a process.** The REST surface — `/functions`, `/datapoints`, `/subscribe`, `/subscriptions` — is nginx-embedded Lua (`content_by_lua_file`) with **no process of its own**, so it answers whenever nginx is up, while the daemon that regenerates the export *and* delivers callbacks is a separate process (`lua /lib/apps/daemon.lua apit3 …`, pidfile `/var/run/apps-daemon-apit3.pid`). The half that answers requests does not depend on the half that maintains the export, which is why the freeze is structurally invisible from the API and why the same dead process also explains the silent-push item below.
- Control and status slots collapse into **one** datapoint (value = status object, write = control object), so state is optimistic and write-then-verify must not be added.
- Values are in engineering units: `dpt.scaling` is a percentage (raw 128 → `50`), so never rescale from 0–255. `fct.se8000` is the one function that applies an F→C conversion while still labelling the unit `C`; `datapoints.temperature_in/out` undo and redo it. The read side follows the measurement, the **write side is inferred** and is flagged in the README.
- A KNX height position counts travel *downwards* (0 % = fully up) while Home Assistant counts how far a cover is open, so `cover.py` inverts it. That is the KNX convention, **not** something the API reports — unverified against hardware. The widget's `height-invert` slot does not undermine it: measured 2026-11-22, that slot exports no datapoint, driving it leaves the published height unchanged, and no Touch front-end bundle reads it.
- A shutter's stop is **raw 0**, i.e. the member `decrease` of the `dpt.step` enum `increase,decrease` (measured 2026-11-22: the API write put `00` on the bus, and all three vendor Touch shutter widgets write literal `0` to that slot from their stop button). `cover.py` advertises `STOP` and resolves the member through `enum_member_for_bit`, so an enum with no measured member gets no stop button rather than a guess. The earlier inference said `increase` and was **wrong** — DPT 1.010 has 0 = Stop — which is the case for reading a vendor front-end before trusting a one-sided reading.
- A function is published **before** its datapoints (15 s typically, minutes during config churn), and export is also gated by the widget's `disable_export` setting. So "a function with no datapoints" and "a correctly configured widget missing from the API" are both normal controller states, not bugs.
- One Touch widget can publish **many** functions, of different types (6 for a full 6-gang switch, 25 for a full `se-logic-thermostat`). Group by `schneider:parentFunction`; never key devices by widget id or stop at the first match.
- Collections are not pageable: `?offset=`/`?limit=` are ignored and `meta.collection` always reports the whole set.

## 5. Working rules

- Run `py -3 -m pytest -q tests` and `py -3 -m compileall -q custom_components tools tests` before every commit. The tests mock Home Assistant (see `tests/conftest.py`), so anything touching HA runtime behaviour (config flow, scheduling, registries, hooks) is **not** covered; say so and ask the user to test in a real HA.
- 🪤 **A green local run is not a green CI run, because the two run against different Home Assistants.** `tests/conftest.py` substitutes `MagicMock` modules *only when `homeassistant` is not importable*, which is the owner's machine; the `tests` job installs `pytest-homeassistant-custom-component` from `requirements-test.txt`, so in CI every `homeassistant.*` import is the **real** module and a mock's permissiveness disappears. That is how `test_the_whole_payload_is_assembled_from_a_coordinator` passed locally in `a086d28` and failed every CI run from then until SMA-238: it stubbed `er/dr.async_entries_for_config_entry` but not `er/dr.async_get`, and the real `async_get` raises `RuntimeError: Device registry not set up` on a `hass` whose `data` the test owns. So when a test touches an HA helper, **stub every call it makes**, not just the one that returns the rows — and before trusting a local pass on anything HA-shaped, check the Actions run. To reproduce CI locally: `uv venv --python 3.14` and `uv pip install -r requirements-test.txt` (that pin requires Python ≥ 3.14).
- Keep `widgets.py` and `backup_utils.py` free of Home Assistant imports so they stay unit-testable. When adding an HA import to code that tests import, extend the mocks in `tests/conftest.py` and the stub list in `tools/dump_controller.py`.
- Keep `strings.json` and `translations/en.json` identical. Update `README.md` when behaviour or options change.
- Never print or commit passwords, backup files, raw dumps or the Touch backup JSON. Use `wiser_dump_anon.json` or counts when analysing real data.
- 🪤 **The git-ignore list in §2 is a filename gate, and a list is not a gate.** It names files this repo never commits and says nothing about a secret, a hostname or the owner's real LAN address pasted into a file this repo *does* commit — a doc, a test fixture, a tool docstring. That is exactly how the skillset shipped two live controller credentials inside probe JSON while its own `.gitignore` and its own mandatory redactor both passed them (the redactor's shapes were topology-only; it was never able to look). **This repo is public, so check the content of a commit, not only its filenames.** One credential-shape sweep of the whole tracked tree was run on 2026-11-24: **no credential material**, its ten hits all `"password": "Password"` UI labels in `strings.json`/`translations/en.json`. The same sweep found the owner's real controller address in two tests and two tools, replaced with the `192.168.1.x` placeholder the rest of the tree already uses — use a placeholder (`192.168.1.x`, `10.0.0.5`, `1.2.3.4`) for any host in an example, fixture or docstring, and note that removing such a value later does not remove it from git history.
- Commits: author `bartosekpetr`; end every commit message with `Co-authored-by: Copilot <223556219+Copilot@users.noreply.github.com>`.
- Version bumps: edit `manifest.json` `version`, commit "Release vX.Y.Z: …", annotated tag `vX.Y.Z`. A release is **not** shipped until the GitHub *release* is published for that tag and is neither a draft nor a pre-release — a pushed tag alone is invisible to HACS, which is how v0.8.0 reached GitHub but never reached the user's Home Assistant. See docs/development.md for the push, publish and verify steps.
- Do not "fix" HA-version deprecations without checking `hacs.json` minimum (2024.12.0). Known cosmetic warning: `via_device` in `entity.py` should become `via_device_id` eventually.

  - ✅ **`POST /subscribe` is the channel.** Body is `{"data":[{"id":<dp>,"type":"datapoint"}],"meta":{"url","secret","type":"subscribe.datapoint"}}`, all three `meta` fields required. **A plain `http://` callback is accepted, stored scheme-intact and genuinely delivered** despite the spec saying HTTPS-only — so this is reachable for an ordinary HA install, at the price of values and signature crossing the LAN in clear text. `DELETE /subscriptions/{id}` → 204 and was proven by re-driving the bus and recording silence.
  - The notification is JSON:API, one datapoint per POST, `value` **always a string**, in the same engineering units as `GET /datapoints` (`dpt.scaling` as a percent, enum members by name) and `timestamp` real ISO-8601 UTC — so the existing decoder serves both paths. The subscription silently includes the two automation-trigger virtuals (`11111111-…`); filter inbound by datapoint id.
  - 🪤 **Verify `X-Callback-Signature`.** The `secret` is never echoed; it is the HMAC key. `msg = "POST " + url.path + " HTTP/1.1" + url.authority + Date + str(len(body)) + body`, header = `base64(lowercase_hex(HMAC-SHA256(secret, msg)))` — **base64 of the ASCII hex, not of the digest** — and the `Date` header must be fed in **verbatim** (it is local time mislabelled `GMT`, an hour off the payload's own UTC timestamp, so parsing or re-rendering it breaks the HMAC, and it is not a usable clock). Port `push_lab.verify_callback()`. The construction is not guesswork from the frames: it was read instruction-by-instruction off the delivery daemon's stripped LuaJIT bytecode and then matched against live frames **2 of 2 exactly** (2026-11-23 write-up), so what still has a single witness is *delivery*, not the signature.
  - 🔴 **The `secret` is a signing key the controller keeps in clear.** It is stored in Redis under `meta.secret` beside the callback URL, readable by anything with a root shell or on-box Lua, and never echoed back. So verifying the header rejects a frame tampered with in flight — worth doing, especially over plain HTTP — but it does **not** prove origin: a reader of that key can forge a callback a correct verifier accepts. That is why `push_utils.generate_secret` is a fresh `secrets.token_urlsafe(32)` per config entry, re-generated on every re-assert, absent from the log and from the sensor's attributes, and why a verified frame authorises nothing beyond "this datapoint's value is now X" — keep it that way.
  - 🔴 **A callback is a state notification, not an event.** Changes to one datapoint closer than ~0.8 s are coalesced to the latest value (8 transitions 0.4 s apart delivered 4). Treat every callback as "this is the current value"; never count edges or reconstruct a sequence. At 1 Hz nothing is lost, so casual testing will not show this.
  - 🔴 **Push fails silent and does not self-heal, so polling stays** as a slow backstop with a full re-read on reconnect. Kill the delivery daemon and the subscription stays listed, `GET /subscriptions` and the whole REST surface keep answering 200, and nothing is delivered indefinitely — nothing in the API distinguishes "quiet because idle" from "the daemon is dead" (same daemon whose death freezes the export, §4). A liveness timeout that re-reads `/datapoints` is mandatory, not optional, and the subscription must be re-asserted on startup and after any gap.
  - ✅ **Across a controller reboot the subscription survives and delivery resumes with no re-subscribe** — the channel's last deliberately-unmeasured row, closed **2026-11-25** under a one-time owner authorisation (a reboot of a live house; the rig refuses that leg without it and the run was not repeated). The pinned certificate was unchanged and pre-existing subscriptions were intact. Three things came with it, and the code was already right about all three: 🔴 **a `200` is not evidence push is flowing** — REST answers at **25 s**, the first callback lands at **39.6 s**, so ~15 s of "every endpoint answers and nothing is delivered" is what a *healthy* startup looks like (`_async_assert` ends on `pending` with the fast poll, so only an arriving callback ever slows the cadence); 🪤 **coalescing is far wider for about the first minute** (3 of 7 driven changes, each the latest value; 7 of 7 once settled), which is expected to trip `_push_missed` and land on full-speed polling plus a re-assert; and ⬛ **a subscription is a Redis cache entry, not a database row** — in no SQLite table and in no file on disk, with its only flash copy a snapshot written every 1800 s plus one on clean shutdown (which is *why* the clean reboot preserved it). So an **unclean power loss is inferred, not measured, to lose any subscription younger than that snapshot**, nothing in the 3rd Party API can force a flush, and that inference — not the reboot — is what the slow-beat re-assert insures against.
